# 发版脚本生成指南（给 AI 的提示词）

> 把这份文档交给 AI，并说明“请按这份指南为当前项目生成发版脚本”。
> AI 需要先判断项目适合哪种发布方式，**向用户汇报并等待确认**，确认后才生成文件，
> 最后按「验收清单」自测。

## 0. 使用方式

把本文件交给 AI，并说：

> 阅读 `docs/发版脚本生成指南.md`，按它为当前项目生成发版脚本。

AI 应自己完成：调研技术栈/版本来源/构建方式 → 判断发布类型 → 汇报并等用户确认 →
生成文件 → 在临时分支安全测试 → 按第 10 节报告结果。

生成的文件（尤其根 `package.json`）需要**提交到仓库**后，应用里的「发布新版本」才能读到版本。

## 1. 第一步：判断发布方式

先读项目，不要先写文件。按下面的决策树判断：

```
仓库只有文档 / 图片 / 数据文件，没有构建步骤？
  是 → 纯文件仓库：默认不接入一键发布；
       确实需要整包分发时，按「压缩包发布」处理（第 4.3 节）
  否 ↓
项目需要数据库 / 中间件 / 多个服务一起跑？
  是 → Docker 镜像发布（第 5 节）
  否 ↓
有 Dockerfile / docker-compose / 需要系统级依赖（chromium、libreoffice、CUDA）？
  是 → Docker 镜像发布（第 5 节）
  否 ↓
是桌面应用（Electron / Tauri / Qt / 需要安装向导）？
  是 → 安装包发布（第 4 节）
  否 ↓
能产出单文件可执行程序（Go / Rust / C++ / PyInstaller）？
  是 → 安装包 / 压缩包发布（第 4 节）
  否 ↓
只能产出源码包 / wheel / jar / 前端 dist？
  是 → 压缩包发布（第 4 节）
  否 ↓
无法判断 → 停下来问用户，不要猜
```

判断时必须看实际文件，不能只看 README：

- 依赖与启动方式：`requirements.txt`、`pyproject.toml`、`package.json`、`go.mod`、`Cargo.toml`、`pom.xml`；
- 构建配置：`Dockerfile`、`docker-compose*.yml`、`electron-builder.*`、`setup.py`、`CMakeLists.txt`；
- CI：`.github/workflows/*.yml`；
- 部署文档：`README`、`docs/`、`deploy/`。

**判断结果要能落到具体文件上**，例如：

```
Docker 镜像发布
依据：RAG/docker/backend.Dockerfile、RAGAS/Dockerfile、
      docker-compose.release.yml、依赖 MySQL/MinIO/Milvus
```

### 1.1 混合项目

同时具备两种形态时（例如 Electron 桌面版 + 服务端 Docker 镜像）：

- **不要自己选**，先问用户「主发布渠道是哪个」；
- `deploy/release-artifacts.json` 的 `kind` 只能选一个；
- 另一个产物可以保留独立 workflow，但不纳入「一键发布」。

### 1.2 应用端检测只是参考

应用会按文件特征给出推荐（Dockerfile / docker.yml / electron-builder 等），
但 AI 必须独立调研。判断与应用推荐不一致时，在汇报里说明原因和依据。

## 2. 第二步：汇报并等待确认（硬性要求）

**生成任何文件之前**，先向用户输出以下四项，然后停下来：

```
【项目判断】
发布方式：Docker 镜像发布 / 安装包发布 / 压缩包发布
依据：<具体文件与依赖>

【拟做的事】
将创建：<文件路径与用途>
将修改：<文件路径与改动>
不会做：不提交、不推送、不改 origin、不改远程配置

【验证方式】
- node --check deploy/release.mjs
- git status 检查（只出现预期文件）
- 临时分支试跑 --no-push
```

然后等待用户明确回复「确认」或提出修改意见。

**用户没有确认之前，禁止：**

- 创建或修改 `deploy/release.mjs`、`package.json`、`release-artifacts.json`、workflow；
- 执行 `git add`、`git commit`、`git tag`、`git push`；
- 修改 `origin` 或全局 git 配置。

用户不同意判断或计划时，按用户意见修改后重新汇报，再次等待确认。

## 3. 通用要求（两种发布方式都适用）

### 3.1 目标产物

在项目根目录生成：

| 文件 | 必需 | 作用 |
|---|---|---|
| `deploy/release.mjs` | 必需 | 发版主流程：升版本 → 提交 → 打 tag → 推送 |
| `deploy/release-artifacts.json` | 必需 | 声明发布类型和产物 |
| `package.json`（项目根） | 必需 | 应用读取当前版本号 |
| `deploy/release.bat` | 建议 | Windows 双击入口 |
| `deploy/release.sh` | 建议 | Linux/macOS 命令行入口 |
| `.github/workflows/*.yml` | 必需 | tag 触发构建 |

**只要 `deploy/release.mjs` 存在**，应用里的「⋯ → 发布 → 发布新版本」入口就会出现。

### 3.2 应用端契约

应用会以如下方式调用脚本：

```bash
node <项目根>/deploy/release.mjs --patch --yes --note "发布说明" --no-watch
```

- 工作目录：项目根；
- 非交互：脚本**不能等待 stdin**；
- 退出码：`0` = 成功，非 `0` = 失败；
- stdout/stderr 原样显示在应用弹窗里，请用中文输出。

| 参数 | 说明 |
|---|---|
| `--patch` / `--minor` / `--major` | 指定升哪一位，跳过交互询问 |
| `--yes` | 跳过所有确认；非交互模式必须加 |
| `--note "..."` | 发布说明（写入 commit 和 annotated tag） |
| `--no-push` | 提交 + 打 tag，但不推送、不盯 CI |
| `--no-watch` | 正常推送，但不轮询 CI |
| `--branch <名字>` | 允许在非 main 分支发版（默认拒绝） |

### 3.3 版本来源（硬约束）

应用固定读取**项目根 `package.json` 的 `version`**：

```json
{
  "name": "your-project",
  "version": "1.0.0"
}
```

- Node 项目：直接用现有 `package.json`；
- Python / C++ / Go / 容器项目：在根目录新增这个文件，发版脚本同时更新它和项目自己的版本文件
  （如 `pyproject.toml`、`CHANGELOG.md`、`deploy/version.json`）。

没有根 `package.json`，发布弹窗拿不到当前版本，无法正常发版。
**必须提交到仓库**，只放在工作区不算完成接入。

### 3.4 产物清单

`deploy/release-artifacts.json` 有两种形态，由 `kind` 决定。

**安装包 / 压缩包：**

```json
{
  "items": [
    "your-project-${version}-linux.tar.gz",
    "your-project-${version}-windows.zip",
    "your-project-${version}-source.zip"
  ]
}
```

**Docker 镜像：**

```json
{
  "kind": "docker",
  "images": [
    { "name": "backend",  "image": "ghcr.io/${owner}/${repo}-backend" },
    { "name": "frontend", "image": "ghcr.io/${owner}/${repo}-frontend" }
  ],
  "items": []
}
```

- `kind` 缺省时按安装包处理（兼容旧项目）；
- `${version}` 由应用按当前选择的版本替换；
- `${owner}` / `${repo}` 由应用按 origin 替换，并转小写（GHCR 要求）；
- Docker 项目的 `images[].name` 必须与 workflow matrix 的 `name` 一致。

### 3.5 release.mjs 行为规格

非交互模式（应用调用）：

1. 校验当前目录是 git 仓库；
2. 校验工作区干净：`git status --porcelain --untracked-files=no` 必须为空
   （未跟踪文件不影响，不用拦）；
3. 校验分支：默认必须是 `main`；不是 `main` 时只有传了 `--branch <名字>` 才继续；
4. 读取根 `package.json` 的 `version`，按参数计算下一版本；
5. 检查 tag 是否已存在（本地 `git tag -l <tag>`、远端 `git ls-remote --tags origin <tag>`），
   存在则失败退出；
6. 发布说明 = `--note`；为空时取「上个 tag 以来最新提交主题」，再没有就用 `<tag> 发布`；
7. 升版本并提交 + 打 annotated tag；
8. `--no-push` 时到此结束；
9. 否则 `git push --follow-tags`；
10. `--no-watch` 时到此结束，否则轮询 GitHub Actions。

交互模式（手动运行，无参数）：询问升哪一位 → 发布说明 → 预览并确认 → 执行。

版本号计算：

- patch：`a.b.c` → `a.b.c+1`
- minor：`a.b.c` → `a.b+1.0`
- major：`a.b.c` → `a+1.0.0`

按 SemVer，**不按十进制进位**：`1.9.0` 的 minor 是 `1.10.0`。

### 3.6 分支规则

- 应用调用脚本时**不带 `--branch`**，所以只允许在 `main` 分支发版；
- 当前不在 `main` 时，应用会禁用发布按钮并提示；用户确认后由应用执行
  `git checkout main`，再允许发布；
- 脚本自身在非 `main` 且没有 `--branch` 时必须**拒绝**，不能自动切换分支；
- 工作区有未提交改动时不能切换分支，先让用户处理。

### 3.7 安全测试要求

- 只在**临时分支或临时克隆**上测试，例如 `git checkout -b release-script-test`；
- **禁止** `git push`、修改 remote、真正发版；
- **禁止** 在有用户未提交改动的目录执行 `git reset --hard`、`git checkout -- .` 等会丢改动的命令；
- 测试后删除临时分支和测试 tag，切回原分支，确认工作区没有残留改动；
- 如果项目当前有未提交改动，先报告，不要强行测试。

### 3.8 提交与 tag

Node 项目可直接用：

```bash
npm version <level> -m "<tag>：<note>"
```

非 Node 项目需要手动实现等价步骤：

```bash
# 更新根 package.json 的 version，以及项目自己的版本文件
git add package.json <其他版本文件>
git commit -m "<tag>：<note>"
git tag -a "<tag>" -m "<tag>：<note>"
```

**必须创建 annotated tag**（`-a`），因为 CI 会读取 tag 注释作为 Release 说明。

### 3.9 手动入口

Windows `deploy/release.bat`：

```bat
@echo off
setlocal
chcp 65001 >nul
cd /d "%~dp0.."
node "%~dp0release.mjs" %*
pause
```

Linux/macOS `deploy/release.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
exec node deploy/release.mjs "$@"
```

## 4. 安装包 / 压缩包发布

适用：Electron、桌面应用、单文件二进制、wheel/sdist、前端 dist、源码包。

### 4.1 GitHub Actions 模板

原则：

- `on.push.tags: ['v*']` 触发；
- 构建产物后，用 `gh release create/edit` 创建 Release；
- **Release 正文读取 tag 注释**（去掉 `vX.Y.Z：` 前缀）；
- 上传产物用 `gh release upload ... --clobber`。

公共片段：

```yaml
permissions:
  contents: write

steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0

  # ... 构建步骤 ...

  - name: 发布到 Releases
    env:
      GH_TOKEN: ${{ github.token }}
    run: |
      NOTES="$(git tag -l --format='%(contents)' "$GITHUB_REF_NAME" \
        | sed -E 's/^v[0-9]+\.[0-9]+\.[0-9]+：//')"
      if [ -n "$NOTES" ]; then
        gh release view "$GITHUB_REF_NAME" >/dev/null 2>&1 \
          && gh release edit "$GITHUB_REF_NAME" --notes "$NOTES" \
          || gh release create "$GITHUB_REF_NAME" --notes "$NOTES"
      else
        gh release view "$GITHUB_REF_NAME" >/dev/null 2>&1 \
          || gh release create "$GITHUB_REF_NAME" --generate-notes
      fi
      gh release upload "$GITHUB_REF_NAME" dist/* --clobber
```

### 4.2 各类型构建片段

**Node / Electron**

```yaml
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run build
      # Electron：npx electron-builder --publish never
```

**Python**

```yaml
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install build
      - run: python -m build -o dist
```

单文件可执行程序：

```yaml
      - run: pip install pyinstaller
      - run: pyinstaller --onefile main.py --distpath dist
```

**C / C++**

```yaml
      - run: cmake -B build -DCMAKE_BUILD_TYPE=Release
      - run: cmake --build build --config Release
      - run: cp build/your-app dist/
```

**Go / Rust / Java**

- Go：`go build -o dist/app ./...`
- Rust：`cargo build --release`，产物在 `target/release/`
- Java：`mvn package` 或 `gradle build`，产物在 `target/` 或 `build/libs/`

**混合前端 + 后端（非容器）**

```yaml
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: 构建前端
        run: |
          cd frontend
          npm ci
          npm run build
          mkdir -p ../dist
          zip -r ../dist/your-project-${GITHUB_REF_NAME}-frontend.zip dist

      - name: 构建后端
        run: |
          pip install build
          python -m build -o dist
```

单个 Release 文件不得超过 **2GB**。

### 4.3 纯文件 / 文档仓库

适用：只有 Markdown、图片、PDF、数据文件、模板素材，没有构建步骤的仓库。

**默认不建议接入一键发布**：

- 版本用 `git tag vX.Y.Z` 标记即可；
- GitHub 每个 tag 自动提供 Source code zip / tar.gz；
- 额外维护 `release.mjs` + workflow 收益很低。

确实需要「整包下载」时，才按压缩包发布接入：

1. 根 `package.json`（只放 name/version）；
2. `deploy/release.mjs`（升版本、提交、打 tag、推送，同第 3 节）；
3. `deploy/release-artifacts.json`：

```json
{ "items": ["your-repo-${version}.zip"] }
```

4. `.github/workflows/release.yml`：

```yaml
      - name: 打包资料
        run: zip -r "your-repo-${GITHUB_REF_NAME}.zip" . -x '.git/*'
      - name: 发布到 Releases
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release create "$GITHUB_REF_NAME" --generate-notes || true
          gh release upload "$GITHUB_REF_NAME" your-repo-*.zip --clobber
```

注意：

- 排除 `.git/`、缓存、临时文件；
- 大文件（视频/数据集）不要进 git，也不要打进 zip；用对象存储或 Release 附件单独管理；
- 单个 Release 文件不超过 2GB。

如果用户只是管理笔记/资料，直接建议「不接入」，不要为了接入而接入。

## 5. Docker 镜像发布

适用：依赖多、服务多、需要数据库/中间件/系统级依赖，无法打成单机安装包的项目。

### 5.1 镜像拆分

- 一个服务一个镜像，不要把后端、前端、数据库塞进同一个镜像；
- 自建镜像通常包括：backend、frontend、worker/ragas/mcp 等；
- MySQL、Redis、MinIO、Milvus、Elasticsearch、Gotenberg 等**直接用官方镜像**，不要自建。

### 5.2 Dockerfile 规范

多阶段构建（前端）：

```dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY frontend/package.json frontend/package-lock.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

FROM nginx:alpine
COPY docker/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html
```

Python 后端：

```dockerfile
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY backend/ backend/
```

非 root 运行：

```dockerfile
RUN useradd --create-home --uid 1000 --user-group app \
    && mkdir -p /app/data && chown -R app:app /app/data
USER app
```

`.dockerignore` 必须排除：

```
data/
.venv/
venv/
__pycache__/
frontend/node_modules/
frontend/dist/
.env
.env.*
*.zip
.git/
docs/
tests/
```

**注意**：`.dockerignore` 排除父目录后，`!子文件` 例外规则不生效。
需要保留某个文件时，用 `docker/*` + `!docker/nginx.conf` 这种写法，不要写 `docker/`。

敏感信息一律不进镜像：`.env`、token、私钥、真实内部地址。

健康检查（compose 依赖）：

```yaml
healthcheck:
  test: ["CMD", "curl", "-sf", "http://localhost:8091/api/health"]
  interval: 15s
  timeout: 5s
  retries: 5
  start_period: 20s
```

### 5.3 GitHub Actions 模板

```yaml
name: Docker

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:
    inputs:
      version:
        description: '镜像标签（例如 v0.1.0）'
        required: true
        default: 'latest'

permissions:
  contents: read
  packages: write

jobs:
  build:
    name: ${{ matrix.name }}
    runs-on: ubuntu-latest
    timeout-minutes: 90
    strategy:
      fail-fast: false
      matrix:
        include:
          - name: backend
            context: RAG
            dockerfile: RAG/docker/backend.Dockerfile
          - name: frontend
            context: RAG
            dockerfile: RAG/docker/frontend.Dockerfile
    steps:
      - uses: actions/checkout@v4

      # GHCR 镜像名必须全小写
      - name: 计算镜像名与版本
        id: meta
        run: |
          echo "image=ghcr.io/${GITHUB_REPOSITORY,,}-${{ matrix.name }}" >> "$GITHUB_OUTPUT"
          echo "version=${{ inputs.version || github.ref_name }}" >> "$GITHUB_OUTPUT"

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: ${{ matrix.context }}
          file: ${{ matrix.dockerfile }}
          push: true
          tags: |
            ${{ steps.meta.outputs.image }}:${{ steps.meta.outputs.version }}
            ${{ steps.meta.outputs.image }}:latest
          cache-from: type=gha,scope=${{ matrix.name }}
          cache-to: type=gha,mode=max,scope=${{ matrix.name }}
          provenance: false
```

规则：

- **matrix 与 `release-artifacts.json` 的 `images` 保持一致**；
- 镜像名统一 `ghcr.io/<owner>/<repo>-<服务>`；
- 每个服务独立缓存 scope；
- 默认只构建 `linux/amd64`；需要 arm64 时再加 `platforms`，构建时间会翻倍；
- `provenance: false` 避免旧版 docker 拉取时多一个 attestation manifest；
- 不要把 `GITHUB_TOKEN` 打印到日志。

### 5.4 部署编排（建议）

提供 `docker-compose.release.yml`，让用户不克隆源码也能启动：

```yaml
services:
  rag-backend:
    image: ghcr.io/OWNER/REPO-backend:VERSION
    restart: unless-stopped
    env_file: .env
    ports: ["8091:8091"]
    volumes: ["./data:/app/data"]
    extra_hosts: ["host.docker.internal:host-gateway"]

  rag-frontend:
    image: ghcr.io/OWNER/REPO-frontend:VERSION
    restart: unless-stopped
    depends_on:
      rag-backend:
        condition: service_healthy
    ports: ["80:80"]
```

- 版本通过 `.env` 的 `VERSION` 统一控制；
- 数据目录 bind mount，不放进镜像；
- 外部服务单独一份 `docker-compose.infra.yml`，用官方镜像；
- 写一份 `deploy/README.md` 说明前置依赖、`.env`、启动/升级/回滚、常见问题。

### 5.5 GHCR 包可见性

首次推送后，GitHub 上的包**默认是 private**，即使仓库是公开的。

- 公开仓库、希望匿名拉取：仓库 → Packages → 对应包 → Settings →
  Danger Zone → Change visibility → Public；
- 私有仓库：用户先 `docker login ghcr.io -u <用户名> -p <PAT>`，PAT 需要 `read:packages`；
- 私有镜像不要误设为 Public。

应用「发布历史」会显示镜像地址、拉取命令和压缩后大小（通过 GHCR manifest 计算）。

## 6. 混合项目

- 先问用户主发布渠道，不要自己选；
- `release-artifacts.json` 的 `kind` 只选一个主渠道；
- 另一个渠道可以保留独立 workflow，但不纳入「一键发布」；
- 在报告里说明「主渠道」和「附加产物」的区别。

## 7. 支持矩阵

| 项目类型 | 推荐方式 | 典型产物 | 注意事项 |
|---|---|---|---|
| Node / Electron | 安装包 | AppImage、exe、zip | electron-builder |
| Python | 压缩包 | wheel、sdist、可执行文件 | `python -m build` / PyInstaller |
| C / C++ | 安装包 | Linux 二进制、Windows exe、源码 zip | CMake/Make；Windows 用 MSVC |
| Go / Rust | 安装包 | 单文件二进制 | 交叉编译简单 |
| Java | 压缩包 | jar / war | Maven / Gradle |
| 纯前端 | 压缩包 | dist 压缩包 | 构建后 zip |
| 纯文件 / 文档仓库 | 默认不接入 | 源码 zip（GitHub 自动提供） | 需要整包分发时用 4.3 的压缩包方式 |
| Python 后端 + 前端 + 数据库 | **Docker 镜像** | GHCR 镜像 | 多服务、外部依赖多 |
| 需要系统级依赖 | **Docker 镜像** | GHCR 镜像 | chromium、libreoffice、CUDA 等 |
| 模型权重 / 大数据文件 | **Docker 镜像** | GHCR 镜像 | 权重走下载或挂载 |
| Android | 安装包 | APK / AAB | 安装 Android SDK；签名放 Secrets |
| iOS / macOS 应用 | 安装包 | ipa / dmg | 需要 macOS runner + 证书 |
| 专用硬件 / 商业 SDK / 交互式构建 | ❌ | — | GitHub Actions 无法自动化 |

## 8. 验收清单

生成后必须逐条验证：

1. `node deploy/release.mjs --patch --no-push` 能成功提交版本号并打 annotated tag，且不推送；
2. `git tag -l --format='%(contents)' vX.Y.Z` 能看到发布说明；
3. 撤销测试提交和 tag（只在本地、未推送时）；
4. 在应用里打开「发布」→「发布新版本」：
   - 当前版本正确；
   - 默认发布说明正确；
   - 「本次发布包含」显示提交列表；
   - 「CI 将产出」显示 `release-artifacts.json` 里的内容；
5. 真正发版一次，确认 tag 已推送、CI 触发、Release 正文是发布说明；
6. 新生成的文件（含根 `package.json`）已列出，并提醒用户提交；
7. 当前分支不是 `main` 时，确认应用会提示切换，而不是直接发版；
8. Docker 项目额外验证：
   - 三个（或全部）镜像在 Actions 中构建成功；
   - GHCR 出现 `:<版本>` 和 `:latest`；
   - 匿名 `docker pull` 能拉取（公开仓库）；
   - `docker compose -f docker-compose.release.yml up` 能启动；
   - `.dockerignore` 确认 `.env`、数据目录、`node_modules`、大文件没有进镜像；
   - 包可见性已按第 5.5 节处理。

## 9. 禁止事项

- 不要在用户确认前创建/修改文件或执行 git 写操作；
- 不要修改或重置 `origin` 地址；
- 不要在非交互模式等待用户输入；
- 不要跳过「工作区干净」检查；
- 不要覆盖已存在的本地/远端 tag；
- 不要把 Token、密码写进脚本或提交进仓库；
- 不要在镜像里放 `.env`、token、私钥、真实内部地址；
- 不要用 root 运行容器内应用进程；
- 不要把 `latest` 作为生产环境固定版本；
- 不要自己构建 MySQL / Redis / MinIO / Milvus / ES 等官方镜像；
- 不要把大模型权重、数据集、`node_modules` 放进构建上下文；
- 不要在 CI 日志里 `echo` token；
- 不要在用户没有明确授权时推送 tag 或修改 GHCR 可见性。
