# 发版脚本生成指南（给 AI 的提示词）

> 把这份文档交给 AI，并说明“请按这份指南为当前项目生成发版脚本”。
> AI 需要先判断项目类型，再生成对应文件，最后按「验收清单」自测。

## 0. 使用方式

把本文件交给 AI，并说：

> 阅读 `docs/发版脚本生成指南.md`，按它为当前项目生成发版脚本。

AI 应自己完成：调研技术栈/版本来源/CI → 生成文件 → 在临时分支安全测试 → 按第 10 节报告结果。

生成的文件（尤其根 `package.json`）需要**提交到仓库**后，应用里的「发布新版本」才能读到版本。

## 1. 目标产物

在项目根目录生成：

| 文件 | 必需 | 作用 |
|---|---|---|
| `deploy/release.mjs` | 必需 | 发版主流程：升版本 → 提交 → 打 tag → 推送 → 可选盯 CI |
| `deploy/release.bat` | 建议 | Windows 双击入口，内部调用 `node deploy/release.mjs` |
| `deploy/release.sh` | 建议 | Linux/macOS 命令行入口，内部调用 `node deploy/release.mjs` |
| `deploy/release-artifacts.json` | 可选 | 发布弹窗里「CI 将产出」的清单 |
| `.github/workflows/release.yml` | 可选 | 推 tag 后自动构建并发布 Release |

**只要 `deploy/release.mjs` 存在**，应用里的「⋯ → 发布 → 发布新版本」入口就会出现。

## 2. 应用端契约（必须严格遵守）

应用会以如下方式调用脚本：

```bash
node <项目根>/deploy/release.mjs --patch --yes --note "发布说明" --no-watch
```

- 工作目录：项目根；
- 非交互：脚本**不能等待 stdin**；
- 退出码：`0` = 成功，非 `0` = 失败；
- stdout/stderr 会原样显示在应用弹窗里，请用中文输出。

### 2.1 必须支持的参数

| 参数 | 说明 |
|---|---|
| `--patch` / `--minor` / `--major` | 指定升哪一位，跳过交互询问 |
| `--yes` | 跳过所有确认；非交互模式必须加 |
| `--note "..."` | 发布说明（写入 commit 和 annotated tag） |
| `--no-push` | 提交 + 打 tag，但不推送、不盯 CI |
| `--no-watch` | 正常推送，但不轮询 CI |
| `--branch <名字>` | 允许在非 main 分支发版（默认拒绝） |

### 2.2 应用读取的版本来源（硬约束）

应用后端目前固定读取**项目根 `package.json` 的 `version`**。

因此，无论项目是什么语言，都必须在项目根准备一个 `package.json`：

```json
{
  "name": "your-project",
  "version": "1.0.0"
}
```

- Node 项目：直接用现有 `package.json`；
- Python / C++ / Go 等：在根目录新增这个文件（可以只包含 name/version），发版脚本同时更新它和项目自己的版本文件（如 `pyproject.toml`、`CMakeLists.txt`、`Cargo.toml`）。

如果缺少根 `package.json`，发布弹窗会拿不到当前版本，无法正常发版。

**根 `package.json` 必须提交到仓库**，否则应用读不到版本；只放在工作区不算完成接入。

### 2.3 产物清单（可选）

`deploy/release-artifacts.json`：

```json
{
  "items": [
    "your-project-${version}-linux.tar.gz",
    "your-project-${version}-windows.zip",
    "your-project-${version}-source.zip"
  ]
}
```

- `${version}` 由应用按当前选择的版本号替换；
- 没有这个文件时，弹窗显示「产物由项目的 CI 配置决定」，不影响发版。

## 3. `release.mjs` 行为规格

### 3.1 非交互模式（应用调用）

1. 校验当前目录是 git 仓库；
2. 校验工作区干净：`git status --porcelain --untracked-files=no` 必须为空（未跟踪文件不影响，不用拦）；
3. 校验分支：默认必须是 `main`；不是 `main` 时只有传了 `--branch <名字>` 才继续；
4. 读取根 `package.json` 的 `version`，按参数计算下一版本；
5. 检查 tag 是否已存在（本地 `git tag -l <tag>`、远端 `git ls-remote --tags origin <tag>`），存在则失败退出；
6. 发布说明 = `--note`；为空时取「上个 tag 以来最新提交主题」，再没有就用 `<tag> 发布`；
7. 升版本并提交 + 打 annotated tag；
8. `--no-push` 时到此结束；
9. 否则 `git push --follow-tags`；
10. `--no-watch` 时到此结束，否则轮询 GitHub Actions（可用 `https://api.github.com/repos/<owner>/<repo>/actions/runs`）。

### 3.2 交互模式（手动运行，无参数）

按顺序询问：

1. 当前版本与升哪一位（patch/minor/major）；
2. 发布说明（显示默认值，回车使用）；
3. 预览将执行的命令并确认；
4. 执行。

### 3.3 版本号计算

- patch：`a.b.c` → `a.b.c+1`
- minor：`a.b.c` → `a.b+1.0`
- major：`a.b.c` → `a+1.0.0`

按 SemVer，**不按十进制进位**：`1.9.0` 的 minor 是 `1.10.0`，不是 `2.0.0`。

### 3.5 分支规则

- 应用调用脚本时**不带 `--branch`**，所以只允许在 `main` 分支发版；
- 当前不在 `main` 时，应用会禁用发布按钮并提示；用户确认后由应用执行 `git checkout main`，再允许发布；
- 脚本自身在非 `main` 且没有 `--branch` 时必须**拒绝**，不能自动切换分支；
- 工作区有未提交改动时不能切换分支，先让用户处理。

### 3.6 安全测试要求

生成后测试必须遵守：

- 只在**临时分支或临时克隆**上测试，例如 `git checkout -b release-script-test`；
- **禁止** `git push`、修改 remote、真正发版；
- **禁止** 在有用户未提交改动的目录执行 `git reset --hard`、`git checkout -- .` 等会丢改动的命令；
- 测试后删除临时分支和测试 tag，切回原分支，确认工作区没有残留改动；
- 如果项目当前有未提交改动，先报告，不要强行测试。

### 3.7 发布前检查（应用端）

应用在打开发布弹窗时会检查以下文件是否已经在 `origin/main` 上：

- 根 `package.json`
- `deploy/release.mjs`
- `.github/workflows/*.yml`

缺任意一个时，弹窗会提示：

> 以下发版文件还没推送到 main：…
> 现在发布只会打 tag，GitHub 不会构建安装包。

发布不会被阻止，但用户应先把这些文件提交并推送，否则推 tag 不会触发 CI。

### 3.4 提交与 tag

Node 项目可直接用：

```bash
npm version <level> -m "<tag>：<note>"
```

它会提交 `package.json` / `package-lock.json` 并创建 annotated tag。

非 Node 项目需要手动实现等价步骤：

```bash
# 更新根 package.json 的 version，以及项目自己的版本文件
git add package.json <其他版本文件>
git commit -m "<tag>：<note>"
git tag -a "<tag>" -m "<tag>：<note>"
```

**必须创建 annotated tag**（`-a`），因为 CI 会读取 tag 注释作为 Release 说明。

## 4. Windows 入口 `release.bat`

```bat
@echo off
setlocal
chcp 65001 >nul
cd /d "%~dp0.."
node "%~dp0release.mjs" %*
pause
```

- 文件名必须 ASCII；
- `chcp 65001` 后，`bat` 里的中文输出才不会乱码；
- 文件里尽量只保留 ASCII 注释。

## 5. Linux 入口 `release.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
exec node deploy/release.mjs "$@"
```

## 6. GitHub Actions 模板（可选）

原则：

- `on.push.tags: ['v*']` 触发；
- 构建产物后，用 `gh release create/edit` 创建 Release；
- **Release 正文读取 tag 注释**（去掉 `vX.Y.Z：` 前缀）；
- 上传产物用 `gh release upload ... --clobber`。

公共片段：

```yaml
permissions:
  contents: write

steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0

  # ... 构建步骤 ...

  - name: 发布到 Releases
    env:
      GH_TOKEN: ${{ github.token }}
    run: |
      NOTES="$(git tag -l --format='%(contents)' "$GITHUB_REF_NAME" \
        | sed -E 's/^v[0-9]+\.[0-9]+\.[0-9]+：//')"
      if [ -n "$NOTES" ]; then
        gh release view "$GITHUB_REF_NAME" >/dev/null 2>&1 \
          && gh release edit "$GITHUB_REF_NAME" --notes "$NOTES" \
          || gh release create "$GITHUB_REF_NAME" --notes "$NOTES"
      else
        gh release view "$GITHUB_REF_NAME" >/dev/null 2>&1 \
          || gh release create "$GITHUB_REF_NAME" --generate-notes
      fi
      gh release upload "$GITHUB_REF_NAME" dist/* --clobber
```

### 6.1 Node / Electron

```yaml
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run build
      # Electron 项目示例：npx electron-builder --publish never
```

### 6.2 Python

```yaml
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install build
      - run: python -m build -o dist
```

需要单文件可执行程序时，可加 PyInstaller：

```yaml
      - run: pip install pyinstaller
      - run: pyinstaller --onefile main.py --distpath dist
```

### 6.3 C / C++

```yaml
      - run: cmake -B build -DCMAKE_BUILD_TYPE=Release
      - run: cmake --build build --config Release
      - run: cp build/your-app dist/  # 按实际产物路径调整
```

Windows 产物用 `windows-latest` 的 MSVC；Linux 用 `ubuntu-latest`。多平台可拆成 matrix job。

### 6.4 Go / Rust / Java

- Go：`go build -o dist/app ./...`
- Rust：`cargo build --release`，产物在 `target/release/`
- Java：`mvn package` 或 `gradle build`，产物在 `target/` 或 `build/libs/`

### 6.5 混合项目（Python 后端 + JS 前端）

分别构建，再合并：

```yaml
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: 构建前端
        run: |
          cd frontend
          npm ci
          npm run build
          mkdir -p ../dist
          zip -r ../dist/your-project-${GITHUB_REF_NAME}-frontend.zip dist

      - name: 构建后端
        run: |
          pip install build
          python -m build -o dist
```

也可以把前端 `dist` 放进后端静态目录后统一打一个包。

## 7. 支持矩阵

| 项目类型 | 能否自动打包 | 典型产物 | 注意事项 |
|---|---|---|---|
| Node / Electron | ✅ | AppImage、exe、zip | 参考 svn-git 的 release.yml |
| Python | ✅ | wheel、sdist、PyInstaller 可执行文件 | 需要 `python -m build` / pyinstaller |
| C / C++ | ✅ | Linux 二进制、Windows exe、源码 zip | CMake/Make；Windows 用 MSVC |
| Go / Rust | ✅ | 单文件二进制 | 交叉编译简单 |
| Java | ✅ | jar / war | Maven / Gradle |
| 纯前端 | ✅ | dist 压缩包 | 构建后 zip |
| 脚本类 | ✅ | 源码 zip | 无构建步骤 |
| Android | ⚠️ 需配置 | APK / AAB | 安装 Android SDK；签名放 Secrets |
| iOS / macOS 应用 | ⚠️ 需付费/签名 | ipa / dmg | 需要 macOS runner + 证书 |
| 专用硬件 / 商业 SDK / 交互式构建 | ❌ | — | GitHub Actions 无法自动化 |

单个 Release 文件不得超过 **2GB**。

## 8. 验收清单

生成后必须逐条验证：

1. `node deploy/release.mjs --patch --no-push` 能成功提交版本号并打 annotated tag，且不推送；
2. `git tag -l --format='%(contents)' vX.Y.Z` 能看到发布说明；
3. 撤销测试提交和 tag（只在本地、未推送时）；
4. 在应用里打开「发布」→「发布新版本」：
   - 当前版本正确；
   - 默认发布说明正确；
   - 「本次发布包含」显示提交列表；
   - 「CI 将产出」显示 `release-artifacts.json` 里的内容（或通用提示）；
5. 真正发版一次，确认 tag 已推送、CI 触发、Release 正文是发布说明；
6. 新生成的文件（含根 `package.json`）已列出，并提醒用户提交；
7. 当前分支不是 `main` 时，确认应用会提示切换，而不是直接发版。

## 9. 禁止事项

- 不要修改或重置 `origin` 地址；
- 不要在非交互模式等待用户输入；
- 不要跳过「工作区干净」检查；
- 不要覆盖已存在的本地/远端 tag；
- 不要把 Token、密码写进脚本或提交进仓库；
- 不要在没有 `--push` 明确授权时自动推送（默认行为要与现有脚本一致）。

## 10. 给用户的最终报告

生成并测试完成后，报告：

- 项目类型判断与依据；
- 生成的文件清单；
- 版本号同步了哪些文件；
- 产物清单（`release-artifacts.json`）；
- 测试命令与结果（临时分支/清理情况）；
- 当前分支与发版前提（例如需要先切到 `main`）；
- 风险、假设和未完成项。
