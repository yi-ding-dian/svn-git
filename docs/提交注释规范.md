# 提交注释规范

按这份写提交信息（git commit）。目标读者不是机器，是**半年后的自己和协作者**——
那时谁都记不清细节，一眼要能看懂"这条改了什么、为什么改"。

## 格式

```
类型：一句话标题（做了什么）

（空一行，可选）为什么改、关键决策、踩过的坑
```

## 五类前缀（标题开头 + 全角冒号「：」）

| 前缀 | 什么时候用 | 例子 |
|---|---|---|
| `新增：` | 别人能**感知到的新能力** | `新增：仓库浏览支持搜索当前目录所有文件` |
| `修复：` | 坏的修好了 | `修复：刷新后最近项目角标不更新` |
| `优化：` | 原来能用、改得更好（体验/性能/文案） | `优化：通知气泡点按即收回` |
| `重构：` | 外面看不出行为变化的结构调整 | `重构：任务 store 收敛为模块级单例` |
| `清理：` | 删死代码 / 死文件 / 无用依赖 | `清理：删除 task-banner 死文件` |

吃不准时按这个顺序判断：**用户能感知的新能力 → 新增；已有功能变好 → 修复或优化；
外面看不出变化 → 重构或清理。** 选最接近的即可，不必纠结。

## 其他规矩

- **标题一句话**（约 40 字内）：只写"做了什么"；细节、次要改动放正文
- **正文写"为什么"和坑**，不写验证/测试过程（"验证：…"、"构建 eslint 全绿"这类都不写）
- **不加署名行**（`Co-Authored-By` 等）
- 一个提交尽量一件事；顺手改的用「顺带：」列在正文
- 标题不写"了"："修复：角标不更新" 而不是 "修复了角标不更新的问题"

## 例子

反例（扫历史时毫无信息量）：

```
更新代码
fix bug
修改一下
```

正例：

```
新增：仓库浏览搜索当前目录所有文件

- 后端 /api/repo-search：svn ls -R 流式过滤，匹配满 200 即杀进程早停；
  完整跑完的目录缓存 30 分钟（防匿名限流）
- 范围与选中分离：否则"点开一个结果"会把下次搜索范围悄悄换掉
```

```
修复：刷新后最近项目角标不更新

- 探测只在开/切项目时跑 + 后端 30s 缓存挡住了重探（用户实报"刷新后 ↑18 是旧的"）；
  当前项目改为强制绕过后端缓存
```
